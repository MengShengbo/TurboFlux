## 摘要

仓库级代码定位要求系统从自然语言问题出发，在大型、异构且缺少统一索引的代码库中识别最可能需要修改的实现文件。现有方法通常在两类取舍之间摇摆：纯词法或图结构检索速度快、成本低，但难以处理间接所有权、跨层传播和语义改写；完全由大语言模型驱动的探索更灵活，却容易产生高尾延迟、重复工具调用、上下文膨胀和不可核验的结果。本文提出 FastContext，一种模型引领、确定性执行、证据约束的自适应仓库检索系统。模型仅负责查询改写、下一跳选择、候选排序、前沿完整性判断与停止决策；本地执行层负责并行搜索、文件读取、符号追踪、精确调用缓存、进展增量反馈与机械证据校验。系统通过结构化代码地图提交协议，将每个候选路径与已读取行区间绑定，并将原始工具历史隔离在子代理内部，从而控制主代理上下文增量。本文在 SWE-bench Verified 与 SWE-PolyBench Verified 构成的 200 题主实验以及 100 题三重复确认实验上，对 FastContext、Claude Code 只读检索和 OpenCode Explore 进行同模型、无原生推理条件下的受控比较。最终稿将报告检索质量、延迟、调用成本、可靠性、重复稳定性与多维切片结果；本文当前版本不对尚未完成的正式实验作定量结论。

**关键词：** 仓库级代码检索；代码定位；软件工程智能体；工具增强语言模型；自适应停止；证据约束

## 1 引言

真实软件维护任务很少能由单个函数的局部上下文充分描述。缺陷报告可能只给出用户可见现象，而真正的修改点位于配置解析、协议适配、状态传播或框架扩展层；一个看似局部的行为还可能同时涉及定义端、消费端、同步实现和兼容分支。因此，面向软件工程智能体的代码检索并不是普通文本搜索，而是从问题陈述到潜在修改集合的因果定位过程。

仓库级代码定位至少包含五个相互依赖的问题：如何把自然语言症状转换为可执行查询；如何在第一次命中后追踪调用关系和数据流；如何判断当前证据是否足以覆盖修改前沿；如何在继续探索与及时停止之间取得平衡；以及如何保证最终候选确实由读取过的源码支持。词法检索、向量检索和静态代码图能够提供高吞吐候选，但它们很难独立决定“下一步应该查什么”。相反，通用工具型代理可以动态规划，却常在重复搜索、无效邻域扩张和长工具历史上消耗大量时间与上下文。

FastContext 的核心判断是：语义决策不应由脆弱的本地启发式取代，确定性执行也不应交给语言模型逐步模拟。系统因此采用明确的职责分离。语言模型引领检索方向并判断何时停止；本地层只执行可验证、可并行、可缓存的操作，并向模型返回机械进展差量。该设计不是把传统检索器包装成代理，也不是构造一个无限探索的通用子代理，而是在有限轮次内形成“规划—执行—反馈—提交”的闭环。

本文的主要贡献如下：

1. 提出一种模型引领、确定性执行的仓库级代码定位架构，将语义决策与机械执行划分为可审计的责任边界。
2. 设计自适应停止与前沿完整性协议，使系统依据未解决的具体路径或符号决定是否继续，而非使用固定检索轮数。
3. 提出并行符号追踪、精确调用缓存和波次增量反馈机制，在保留动态语义追踪能力的同时减少重复请求和低信息增益工具调用。
4. 设计读取证据账本与结构化代码地图提交协议，拒绝未被 `read_file` 覆盖的候选与关系，提升结果可核验性。
5. 建立包含 1,500 次系统运行的冻结对照实验，统一模型、推理设置、权限、超时和数据集，分别评估广度与重复稳定性。

## 2 问题定义

给定代码仓库快照 \(R\)、自然语言任务 \(q\) 与实现文件集合 \(F\)，仓库级代码定位系统输出一个至多包含 \(k\) 个文件的有序列表 \(L_k(q, R)\)。基准数据给出真实修改文件集合 \(G\subseteq F\)。系统目标不是生成补丁，而是在有限成本下最大化真实修改文件的召回与排序质量。

本文使用 Recall@\(k\)、MRR、MAP、nDCG@10 与 Full@10 衡量定位质量。由于可用性同样受运行失败、超时与延迟影响，失败运行按零质量计入主指标，并同时报告成功率、超时率、延迟分位数、模型请求数、工具调用数和 token 使用量。该定义避免只在成功子集上报告检索质量而掩盖系统可靠性。

FastContext 的输出不是任意相关文件列表，而是面向后续编辑的代码地图。候选需要描述其角色、修改概率、因果距离和修改影响；候选行区间必须落在本轮实际读取证据内。系统允许显式报告未解决的编辑路径，但不允许把未读取候选伪装成已验证结果。

## 3 相关工作

### 3.1 仓库级检索与代码定位

RepoCoder 通过迭代检索改善仓库级代码补全，说明一次性相似度检索不足以覆盖跨文件依赖 [@zhang2023repocoder]。Repoformer 进一步研究选择性检索，强调并非每个任务都应支付相同检索成本 [@wu2024repoformer]。CodeRAG-Bench 对代码检索增强生成进行系统评估，表明检索器性能、查询形式与下游任务之间存在显著耦合 [@wang2024coderagbench]。这些工作主要关注检索增强生成或补全；FastContext 面向问题驱动的修改文件定位，并把动态查询改写和证据提交纳入同一闭环。

### 3.2 软件工程代理与工具使用

ReAct 将推理与动作交替组织，为语言模型驱动的工具代理提供了通用范式 [@yao2023react]；Toolformer 展示了模型学习使用外部工具的可能性 [@schick2023toolformer]。在软件工程领域，AutoCodeRover 与 Agentless 分别探索代理式程序改进和简化的软件修复流程 [@zhang2024autocoderover; @xia2024agentless]。Claude Code 与 OpenCode 则提供了工程化的只读探索或子任务机制 [@anthropicclaudecode; @opencode]。FastContext 关注其中更窄但关键的阶段：在补丁生成前快速形成可核验的修改候选集合。

### 3.3 自反思、选择性检索与图引导

Self-RAG 将检索与自反思决策结合，说明检索时机和证据质量可由模型动态控制 [@asai2024selfrag]。图引导代码定位方法利用符号关系、调用边和结构邻接缩短跨文件追踪路径。FastContext 接受图或符号工具作为可选执行手段，但不让静态图的可用性决定主流程；是否追踪某个符号、何时停止以及如何排序仍由模型基于任务和新证据判断。

### 3.4 评测基准

SWE-bench 以真实 GitHub 问题和仓库快照评估软件工程系统 [@jimenez2024swebench]。SWE-bench Verified 对样本可解性进行人工验证，SWE-PolyBench Verified 扩展了语言与仓库类型 [@swebenchverified; @swepolybenchverified]。本文从二者构建平衡的代码定位语料，使用真实补丁涉及的实现文件作为 gold paths。与完整修复评测不同，本文隔离检索阶段，以便分析代理架构本身的定位质量、成本和稳定性。

## 4 FastContext 架构

### 4.1 总体流程

FastContext 作为主代理的隔离子代理运行。输入包含任务描述与工作区结构摘要；输出为紧凑的 `fast_context_pack`，其中包括检索状态、已验证代码地图、证据范围和未解决项。完整工具历史不会进入主代理上下文。

一次运行由以下循环构成：

1. 模型根据任务、仓库结构和已有证据形成当前检索前沿。
2. 模型在搜索、文件发现、单符号追踪、多符号追踪和文件读取工具中选择一个或多个动作。
3. 本地执行层并行执行同一波次的工具调用，并复用完全相同的成功调用。
4. 系统向模型返回原始结果以及本波次机械差量，包括新增读取路径、新增发现路径、新增证据范围、重复调用、空结果和工具错误。
5. 模型判断是否存在仍可能改变候选集合的具体未读路径或未解析符号。若存在则继续；否则提交结构化代码地图。
6. 提交校验器检查候选和关系是否由读取证据覆盖。失败提交被拒绝，并允许模型在剩余轮次内修正。

系统允许最多 8 个模型轮次，每波最多并行 8 个工具调用。该上限是失控保护，不是固定预算；简单任务可以在更少轮次结束。

### 4.2 模型与本地层的责任边界

FastContext 将决定质量上限的语义操作交给模型：

- 将症状改写为实现概念、符号、配置项或协议路径；
- 判断搜索命中是否对应真正所有者、消费者、传播层或测试旁路；
- 从源码输出选择下一跳符号与文件；
- 判断编辑前沿是否完整；
- 独立于发现顺序对候选排序；
- 决定停止、继续或显式失败。

本地层仅执行具有明确输入输出语义的操作：

- 内容搜索与文件名搜索；
- 文件区间读取；
- 单符号和批量符号追踪；
- 同波次并发调度；
- 精确成功调用缓存；
- 读取证据账本维护；
- 结构化参数和证据范围校验；
- 进展差量统计与历史压缩。

该边界避免两种常见失效。其一，本地启发式根据词频或固定规则替模型决定“相关性”，会在间接所有权和短问题描述上产生系统性盲区。其二，让模型逐项完成文件枚举、去重和覆盖判断，会增加调用次数并产生不可重复的机械错误。

### 4.3 工具集合

FastContext 暴露六类工具：`search_content` 用于精确或正则内容检索；`search_files` 用于路径模式发现；`trace_symbol` 用于围绕单个具体符号追踪定义和引用；`trace_symbols` 在同一前沿内并发解析 2–4 个具体符号；`read_file` 建立行级证据；`submit_code_map` 提交最终结果。

`trace_symbols` 不是无界图遍历。模型必须先从问题或源码中提出具体符号，本地层再并发执行追踪。这样既保留模型驱动的下一跳选择，又把多个独立查询压缩到一个工具波次。

### 4.4 自适应停止

固定轮数会同时伤害简单任务与复杂任务：前者被迫继续，后者又可能在前沿未闭合时停止。FastContext 的停止条件以“是否仍存在能实质改变有序修改集合的具体未读前沿”为中心。模型若决定继续，必须通过下一次工具调用体现该前沿；仅为了增加信心、补充泛化示例或搜索邻近测试而继续不被视为充分理由。

每一波完成后，系统返回新增路径数、读取范围、重复调用、空结果与错误。该反馈只描述机械进展，不替代语义判断。连续无新信息或完全重复调用是停止信号，但最终是否停止仍由模型结合任务目标决定。

### 4.5 精确调用缓存与历史压缩

工具缓存键由工具名和规范化参数组成。仅成功结果进入缓存，失败、超时与不完整结果不会缓存。完全重复的调用直接复用结果并显式标记，避免把缓存命中误认为新证据。

随着工具波次增长，旧搜索输出会被压缩，而最近两个工具波次保持完整。最终提交前，系统生成读取证据账本，保留路径和已覆盖行区间。该策略减少长历史对模型输入的重复占用，同时保证最终证据校验不依赖被压缩的自然语言摘要。

### 4.6 证据约束代码地图

`submit_code_map` 必须独立调用。每个候选包含路径、行区间、角色、置信度或等价排序信息；关系包含源、目标与证据位置。校验器要求所有候选行区间和关系证据均被本轮 `read_file` 结果覆盖。若仍存在模型已知的高概率未读修改点，则模型应继续检索或将其列为未解决前沿，而不是提交虚假的完整状态。

证据约束并不保证候选一定正确，但它消除了“未读即引用”这一类可机械检测的错误，并使后续主代理能够按需复核最关键范围。

## 5 实验设计

### 5.1 研究问题

- **RQ1：检索质量。** FastContext 能否在统一模型条件下提高真实修改文件的召回与排序质量？
- **RQ2：效率。** FastContext 的延迟、模型请求、工具调用和 token 成本与通用探索代理相比如何？
- **RQ3：可靠性。** 三套系统在超时、协议失败、工具失败和输出契约失败方面有何差异？
- **RQ4：泛化。** 结果在数据集、语言、仓库、任务类别、gold 文件数量和检索链复杂度切片上是否稳定？
- **RQ5：重复稳定性。** 同一任务重复运行三次时，各系统的质量、排序和成本方差如何？

### 5.2 数据集与样本

主实验包含 200 个任务，其中 100 个来自 SWE-bench Verified，100 个来自 SWE-PolyBench Verified。语料覆盖 Python、Java、JavaScript 与 TypeScript，并保留任务的原始仓库、基准提交、问题描述和真实修改文件。确认实验使用冻结的 100 题子集，每套系统重复运行三次。

样本的 gold paths 来源于真实补丁修改文件。主分析优先报告实现文件定位；测试文件、生成文件与仅格式变化文件的处理规则由数据准备脚本固定并记录。历史开发中已查看过的公开任务可能造成污染，因此确认实验明确披露“公开任务暴露”限制，不将其描述为严格未见测试。

### 5.3 对照系统与公平性

比较系统为 FastContext、Claude Code 只读探索和 OpenCode Explore。三者使用同一 API 配置、同一 `gpt-5.5` 模型，并关闭原生推理强度。权限限制为仓库读取与搜索，不允许编辑、运行测试或联网获取答案。每次运行硬超时为 600 秒；瞬时故障最多重试三次；系统顺序按任务轮换，以降低时间和服务负载偏差。

主实验共 600 次运行，确认实验共 900 次运行，总计 1,500 次。任务级并发上限为 25，控制器从 4 开始，根据限流、超时和请求延迟自适应调整。并发只影响吞吐，不改变单次运行的工具权限和任务内容。

### 5.4 指标

质量指标包括 Recall@1/3/5/10、Precision@5、MRR、MAP、nDCG@10 和 Full@10。可靠性指标包括成功率、超时率以及按 `protocol`、`authentication`、`rate_limit`、`model`、`tool`、`output_contract`、`repository` 和 `unknown` 分类的失败率。效率指标包括端到端延迟 p50/p95、API 时间、请求数、重试数、搜索调用、读取调用、总工具调用、输入/输出/cache/reasoning token 与可获得时的美元成本。

失败和超时在质量汇总中计为零；延迟和调用均值同时报告全体运行与成功运行口径。每个重复实验先在任务内求均值，再跨任务计算总体指标，避免把重复次数当作独立样本扩大显著性。

### 5.5 统计方法

主指标以任务为抽样单位，采用 10,000 次 bootstrap 计算 95% 置信区间。系统间比较使用配对置换检验，并报告均值差、胜/负/平计数和效应量。确认实验包含多个指标和两组主要比较，最终稿将明确多重比较校正方法，并将 Recall@10 预先指定为主要质量指标。重复稳定性通过任务内标准差、变异系数和排名一致性报告。

### 5.6 可复现性

正式实验冻结 FastContext 实现提交、实验工具链提交、数据清单 SHA-256、模型名、推理设置、CLI 版本、随机种子、超时和并发策略。每次完成运行立即追加到 JSONL 日志；相同 `runId` 重启时保留最新记录；失败不会被静默删除。最终发布包将包含逐题 CSV/JSON、聚合数据、图表数据、失败审计、运行协议和论文生成脚本。

## 7 讨论

FastContext 的设计假设是，仓库检索的关键瓶颈不是缺少更多本地启发式，而是缺少快速、受约束的语义控制。若正式结果显示质量提升但延迟没有改善，说明模型引领路径有效而停止或请求复用仍不足；若延迟下降但多文件召回受损，则需要改进前沿完整性而非增加固定轮次；若特定语言或仓库显著退化，应优先检查符号工具与路径规范化，而不是改变全局语义策略。

结果解释还应区分“检索相关”与“补丁必要”。真实补丁文件是可审计标签，但同一问题可能存在其他合理修复位置；反之，补丁包含的同步文件可能不需要在第一轮定位中全部出现。本文因此同时报告有序召回、完整覆盖和逐例审计，不把单一指标视为全部工程价值。

## 8 有效性威胁

**构念有效性。** gold paths 由历史补丁定义，不一定等价于唯一正确修改集合。文件级指标也无法评价行级解释质量。本文通过多指标、证据审计和案例分析缓解该问题。

**内部有效性。** 三套系统虽使用同一模型，但协议适配、提示词、工具定义和 CLI 实现不同，这正是被测系统的一部分，同时也意味着结果不能归因于单一模块。共享中转 API 可能引入缓存与负载波动；顺序轮换、并发控制和重复实验用于降低影响。

**外部有效性。** 数据来自开源仓库和问题修复任务，不能直接代表私有单体仓库、生成代码、超大型多仓或非缺陷类探索。语料只覆盖四种主要语言。

**结论有效性。** 公开基准可能被基础模型见过，且部分任务曾用于历史开发调试。最终结论必须以冻结协议、确认矩阵和效应量为依据，不使用挑选案例支持总体优越性。

## 9 结论

本文提出 FastContext，将仓库级代码定位组织为模型引领的语义控制循环，并由确定性执行层提供并行工具、精确缓存、机械反馈和读取证据约束。该架构试图在通用探索代理的灵活性与传统检索器的速度、可重复性之间建立清晰边界。关于其相对质量、速度和稳定性的最终结论将在 1,500 次冻结实验全部完成后由同一数据流水线生成。
