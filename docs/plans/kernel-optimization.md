# TurboFlux 内核优化执行计划

状态：首批基准入口、主模型及压缩请求账本、V2回放与工作台摘要已实现并验证；完整任务套件、子Agent逐尝试账本及性能候选实验继续推进。
版本：2026-09-20。主实施目录：`desktop/`。

目标是持续提高真实任务的完成质量和效率，直到在固定任务集、当前模型路由与机器上，没有经过验证且值得保留的高收益改动。这里把“优化到极限”落实为有证据的阶段性收敛，不把单次高缓存率或跑完清单称作绝对极限。

## 目标与硬约束

| 指标 | 验收方式 |
| --- | --- |
| 任务正确性 | 所有固定验收断言通过；真实任务完成率不低于基线；任何破坏文件、越权执行、遗漏终态或错误恢复均否决候选 |
| 完整任务缓存 | 持续以固定真实工程套件加权命中率 ≥95% 为目标；包含首次请求、重试和失败恢复，同时公开逐任务与冷/热阶段结果 |
| 无效消耗 | 追踪额外声明、空轮询、重复检索、错误编辑返工；已确认由内核故障导致的重复消耗须消除 |
| 任务效率 | 比较任务耗时、模型尝试数、未缓存输入、输出 token、工具执行数与内存；候选至少改善一个主指标且没有质量或关键尾延迟退化 |
| 优化幅度目标 | 在质量不降前提下，以整套任务中位耗时和未缓存输入较新的有效基线各减少20%作为挑战目标；待重复基线建立后校准，不能当作收益承诺 |
| 数据完整性 | 单次用量、累计用量、失败尝试与历史回放可对账；未知用量保持 unknown，不能用0替代；缓存 token 不重复加入 input |
| 可维护性 | 职责与数据所有权明确、依赖无环、改动可单独撤销；只保留有收益或明确正确性价值的抽象 |

如果95%未达到，继续标记目标未达成并列出损失来源。不得通过填充无用上下文、重复发送相同请求、删除冷启动样本、延长任务或降低验收要求抬高比例。缓存率上升但任务更慢或更贵，不视作优化成功。

## 当前起点：已确认与待验证分开

证据基线见 [baseline.json](/Users/apple/Desktop/TurboFlux/artifacts/kernel-optimization-plan-20260920/baseline.json)。

- 单条真实工程任务：23分钟、23次模型请求、32次工具调用；输入856,333、缓存784,256、输出40,750，完整命中率91.58%。工程64项测试和62项独立验收通过。
- 上述任务72,077个未命中 token 中，53,262为首次请求/首次发送的新内容与框架开销，18,815为旧内容再次未命中。大段新补丁的首次回传占25,248 token。
- Codex本机近期可核验样本28个会话、1,182次请求，加权95.32%；一个145请求工程会话完整97.59%，其最初23次为92.86%。这些是参照，不是同任务对照，也不构成内核上限。
- 字面编辑、历史工具证据保留、稳定缓存键、Responses参数稳定和实际请求计时修复仍存在于当前源码。近期还已改进工具生命周期、唯一任务终态与界面增量投影，不能重复计为新优化成果。
- 当前V2会话事件契约和转换器仍没有`usage.updated`持久化分支。原始用量事件在内存中存在，但历史可追溯性不完整：这是优先补齐的事实缺口。
- `responseMode.ts`仍要求每个新用户请求先单独调用一次模式声明，之后才执行工作。要验证能否减少这一往返，必须保留声明与执行约束。
- `ModelSurface`仍对历史进行投影复制、指纹比较；工具批次以整个批次的`Promise.allSettled`调度。它们是待剖析的候选热点，不是已经证明影响端到端性能的瓶颈。

## 执行路线与依赖

P0 → P1 → P2/P3 → P4/P5 → P6。P2和P3按单项候选逐次实验；一次只改变一个可归因的机制，不混入无关重构。

| 阶段 | 工作 | 主要责任包 | 退出条件 |
| --- | --- | --- | --- |
| P0 | 固定任务套件、冻结版本、建立重复基线 | scripts / artifacts | 能一条命令重现任务、验证产物并生成可对账报告 |
| P1 | 正确性与持久化观测闭环 | contracts / conversations / agent-runtime | 请求及用量重启不丢、不重；已知编辑/取消/重试问题回归通过 |
| P2 | 减少模型往返，统一模型请求边界 | models / agent-runtime | 候选真实任务减少请求或等待，无声明/权限/结果完整性退化 |
| P3 | 减少必要任务之外的新上下文与重复处理 | models / agent-runtime / tools | 新输入或准备开销下降，证据完整性与追问能力保持 |
| P4 | 工具与进程调度、数据新鲜度 | tools / agent-runtime / platform | 可测本地延迟和资源改善，读写/取消隔离不变 |
| P5 | 长会话存储、投影与恢复 | conversations / workbench / presentation | 长会话不发生超线性放大，重启与回放质量稳定 |
| P6 | 同任务比较、压力验收、集成与收敛审查 | 所有相关包 / Desktop / Orbit | 收益可重复、集成可用、剩余瓶颈与未达指标明确列出 |

### P0：把优化变成可重复实验

1. 保存源码摘要、模型/协议/推理配置、固定任务输入、允许的写入目录和独立验收器。基线包含此前修复，不再把旧缺陷修复当成后续收益。
2. 将现有工程运行采集器与验收器整理为版本化测试入口；每次保存请求ID、实际发送指纹、usage、调用结果、时间区间、峰值与释放后的内存。
3. 建立六类任务。人工编写的正确性用例与被测Agent实现分离，验收器不能靠读取实现内容预测答案。

| 任务 | 真实验证内容 | 主要风险 |
| --- | --- | --- |
| B1 工程交付 | workspace依赖检查器或同等规模CLI：实现、测试、失败恢复、实际仓库报告 | 大补丁回传、长输出、编辑正确性 |
| B2 多文件修复 | 从固定缺陷快照修复模块/测试/调用方并执行仓库检查 | 定位效率、修改范围、工具返工 |
| B3 长会话追问 | 完成工作后追加依赖既有证据的问题，并执行一次明确压缩 | 证据丢失、前缀改写、重复读取 |
| B4 中断与恢复 | 文件/命令任务暂停、取消、重启后续接，核对持久化事实 | 迟到结果、重复副作用、重复用量 |
| B5 并发读写 | 真实临时文件、并行检索、写后读取、同内容请求和失败部分写入 | 旧结果、授权绕过、无限并发 |
| B6 桌面完整链路 | 提交工程任务、原生工具、流式界面、历史切换和再启动 | 宿主注入差异、渲染开销、安装包与源码漂移 |

4. 回放/故障注入用于定位本地逻辑与成本；不得把模拟provider命中率作为真实缓存成绩。只对有机制证据的候选运行真实模型。
5. 真实对照固定模型、路由、推理强度、输入与验收器。先用相关任务筛选；候选最终至少三对交替顺序运行。公开每对结果和波动，基线、候选均计入冷启动与失败。冷/热实验维持组内稳定缓存键，实际命中以provider返回为准。
6. 从已有 `workbench-long-session-benchmark.ts`、conversation-v2及Profile基准建立本地对照；在独立临时Profile运行，先确认脚本适配当前结构。

P0当前已完成源码/证据清点、历史23请求回放命令和B2式真实工程入口。真实工程已跑通一次并独立验收；完整B1～B6套件、重复对照与长会话压力基线尚未完成。

### P1：请求、用量与结果必须可恢复、可核账

- 扩充已有契约，明确`conversationId/runId/requestId/attemptId/providerResponseId`的归属；逻辑请求和物理重试分开计数。
- 用量记录包含input/cached/cache-write/output/reasoning的已知口径、来源、是否最终报告；增量与累计不混用。模型输出中的推理用量不重复加到output。
- 最终请求只保存必要指纹、协议/配置版本和时点；诊断默认不保存凭据或整段用户文本。耗时使用单调时钟，墙钟用于跨文件对齐。
- 给V2增加版本兼容的用量和请求诊断事件、转换、投影及恢复。先写新事件与读取兼容，已有日志按实际已存数据恢复；不捏造缺失的历史usage。
- 同一次最终用量重放不得重复累加；中途中断的已知消耗保留；网络失败且上游没有usage必须显式未知。
- 用原始23请求和新固定用例验证：实时汇总、落盘、进程重启后的汇总完全相等；唯一终态、重写generation和文件原子写保持正确。

接口方向：contracts拥有事实类型；models提供标准响应事实；agent-runtime拥有运行/请求关联；conversations拥有落盘与恢复；workbench负责装配，renderer不重新推断用量。

首个实施单：P1-01，用量持久化与回放对账。它修复后续优化无法稳定验收的前置问题。

### P2：减少模型往返与请求漂移

源码入口：`agent-runtime/src/responseMode.ts`、`agentEngine.ts`、`models/src/modelRequestOrchestrator.ts`、`requestCompatibility.ts`及providers。

- 实验A：让模式声明和首步工作在同一响应中表达，由内核先验证声明再执行允许的动作。不得用关键词规则替代模型理解，也不得放宽工具授权；声明缺失/错误时按明确策略处理。以是否减少真实请求及其用量为验收，不假设模型一定遵守。
- 实验B：短命令完成由宿主提供明确终态，评估减少“启动→再问模型→读终端”的空往返。长命令保留后台状态、可取消与可恢复日志，不能静默等待或吞掉错误。
- 把三种协议中重复的请求准备/兼容重试/标准响应汇总从AgentEngine收拢到models的明确入口。transport以契约注入；models不反向依赖tools、UI或Electron。
- 每个物理尝试冻结独立请求与计时，修改参数只能产生新尝试；暂停、取消、限流、部分流与拒绝不能互相污染基线或重试账本。
- 上游能力探测及原生output续接保持独立实验。此前保留原生output未显示缓存收益，因此不作为默认重构目标。变更模型或推理强度只能作为单独标注的实验变量。

通过条件：原任务正确性/权限/声明/取消回归通过；有可重复的请求数、未缓存用量或耗时收益。上游偶发零命中以请求ID记录，不通过盲目重试来掩盖。

### P3：优化真正进入模型的新内容及本地上下文处理

源码入口：`models/src/modelSurface.ts`、`agent-runtime/src/contextManager.ts`、`runtime/agentContextCoordinator.ts`、`contextCompaction*.ts`、`tools/src/workspaceSearch.ts`。

- 先测工具结果、补丁参数、日志、计划快照和模型回答各占多少新增token；按贡献排序。此前最大项是补丁首次回传，应优先用实测验证协议保真与更精确的工程编辑，而不是扩大固定提示词。
- 工具结果在首次进入模型前生成有界且可继续读取的视图：检索命中带范围与文件、命令保留退出码和关键错误、完整输出仍由宿主持有。按任务需要提供证据，不能只截前几行后宣称已读全文件。
- 消除重复包装、无变化快照和重复序列化；不能通过隐藏扫描、漏报错误或擅自删掉已发送历史降低token。
- 剖析`syncTurns/projectTurns/getState`及token统计，必要时增加按不可变revision的缓存/增量索引；编辑历史或显式压缩时准确失效，保持原请求前缀可审计。
- 压缩仅在预算需要或显式触发时发生，保存事实与待办并记录替换原因。重点验证跨轮追问、文件变化后重新读取、图片预算与压缩失败恢复。
- 只对可证明新鲜度的对象考虑复用；没有环境revision的文件、网页、命令结果不能发展为永久“同参数缓存”。

通过条件：固定验收与追问均通过；相关任务新增input、重复处理CPU或内存下降。完整token、命中率、输出量同时报告，任何收益都不能依赖信息缺失。

### P4：工具、I/O与执行资源

源码入口：`runtime/toolExecutionCoordinator.ts`、`toolCallOrchestrator.ts`、`toolExecutionLedger.ts`、`tools/src/nodeToolExecutor.ts`、`runtimeTaskManager.ts`。

- 先测并发批次规模与文件/搜索/进程实际耗时；为独立只读操作建立可控并发，避免大批次瞬间占满句柄或进程。并发度由固定压力数据决定，不盲目增加。
- 保留写屏障、每个调用独立权限检查、取消scope隔离、结果副本隔离及失败部分写入后的失效；先扩充故障回归，再调整调度。
- 合并有证据的重复读、批量检索和系统查询。顺序重复读取默认仍实际执行，除非有可靠版本证据。
- 核对child process、后台终端、MCP连接、文件监听、计时器和流在成功/失败/取消后的释放；上游慢响应不能让内核无限保留工作占用或伪造完成。

通过条件：本地P50/P95、峰值内存或资源峰值有可重复改善；取消/关闭稳定，无遗漏结果、重复副作用或旧文件内容。

### P5：持久化、投影和超长会话

- 使用已有存储与投影基准测试1k/10k/50k事件，以及连续多任务、切换与重启；每档至少五轮本地重复，分离模型耗时。
- 核对event字节、写入次数、索引读取、恢复耗时、峰值与释放后内存。找出重复全量快照、深拷贝和全历史扫描，再定点改为增量。
- 流式文本可有序合并写入，但审批、副作用结果、输入提交、最终用量及run终态必须保留顺序和持久化屏障；异常退出恢复不能猜测成功。
- 长会话只保留必要的活跃投影；冷历史按索引读取。若性能瓶颈确实落到DOM节点，再在renderer包实现可验证的虚拟化，不将UI职责塞入内核。
- 新事件及索引的迁移遵循旧会话可读、失败可恢复和Profile隔离，尤其复测P1用量账本不会因重放重复计算。

通过条件：规模扩大不出现反复全历史扫描导致的超线性放大；新旧投影结果一致，数据恢复断言全通过。已有唯一run完成逻辑保持，不重新引入快照推断终态。

### P6：集成、同任务比较与阶段性收敛

1. 所有保留候选执行类型、相关回归、架构/边界检查和完整工程套件；失败案例保留并计入结果。
2. 与Codex做相同任务、相同验收器、相同模型/推理和接近的路由条件比较。公开实际差异，不把不同任务或不同请求长度的数字当作A/B。
3. 构建候选Desktop，在独立Profile完成首启、真实任务、暂停/恢复、退出重启、历史用量和产物验收；校对安装包来源摘要与测试源码。
4. 可共用补丁显式集成到Orbit worktree，单独构建和验收；不依赖跨worktree源别名或拷贝旧dist。
5. 最终交付逐项前后证据、回滚点、达成/未达目标和剩余外部瓶颈。仅源码通过不等于安装版生效。

只有同时满足以下条件，才能报告“当前条件下已收敛”：高优先级正确性问题清零；所有已确认的高收益候选完成验证；连续三轮不同机制的候选没有超出重复运行波动的净收益，或收益不足以抵消已测退化/复杂度；不存在尚未评估的明确高收益路径。任一指标未达目标如实保留，不能因时间或预算结束就称到极限。

## 实施与审查方式

- 保留当前大量未提交修改。每个实施单保存编辑前摘要与专属补丁，不reset、不覆盖其他线程或worktree的工作。
- 每个候选：问题证据 → 最小实现 → 原始故障/性能复现 → 相关回归 → 必要的真实任务 → 保留或撤销本候选。实现只是完成一部分，验收证据才决定完成。
- 不以文件拆分数量、测试数量或缓存百分比单独判定收益；关注用户任务是否正确完成、是否少等待、少返工和少消耗。
- 本计划是执行依据，无需反复确认普通可逆工程步骤。不会把未运行的实验或未来收益写成已完成。
